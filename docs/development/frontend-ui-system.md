# Frontend UI system

## Design contract

The application page is the visual and behavioral reference for the shared component system, including its dialogs, states and responsive layouts. Changes to shared components and the theme must preserve it. This document describes the maintained UI contracts.

- Extract reusable visual primitives and complete compositions from the protected application page. Preserve its appearance and functionality, including indirect theme effects. Refactoring and responsive improvements must preserve that contract.
- Reuse the existing suitable component exactly. Add a component only when no suitable one exists; add variants only for demonstrated semantic or behavioral needs. Page-specific legacy styling is not such a need.
- Pages own placement and available space. Standalone compositions own their internal layout, may reorder/stretch children, and select supported sizes and tones. They do not independently redefine a ready child control's visual design. Wrapping old markup does not complete migration.
- Width changes do not imply font scaling. A genuine size/density change coordinates text, icons, padding and gaps inside the component with readable text and usable interaction targets. Prefer reflow and intended wrapping to shrinking labels to fit. Implement responsive behavior once in the owning component.
- Delete superseded implementations and unused styles, exports, imports, dependencies and migration-only adapters after checking usage. Audit all composed presentation, not only interactive-control imports. Domain geometry is not an exemption for legacy surface styling.
- Completion requires a component replacement map plus source checks, behavioral tests and visual inspection across routes, states, roles and viewports.

All application controls are composed through `src/shared/ui/index.ts`. MUI/Emotion is the implementation engine, not a second public control library. The language remains Alegreya typography, dark textured surfaces, brass accents and clear semantic actions. Application registration is a protected visual reference.

## Game guide

`/panel/game-guide` is a public read-only guide, including when no game is published. Direct links and section fragments work without signing in. Guests see a language selector and optional Twitch sign-in; no game queries or realtime subscriptions mount. Signed-in readers retain panel navigation. The centered title introduces the game, followed by full-width text explaining loadouts, difficulty, risk and the player/spectator roles. Participation is explained in prose without duplicate role or application-page buttons. The introduction, top index and content sections share one centered column of equal width. The compact corner-framed index sticks below the site header on every screen size. It remains a horizontal row with short, centered, single-line labels; narrow screens scroll the row horizontally instead of wrapping or shrinking the text. The active shortcut stays in view as sections change. Section anchors leave space for both the site header and the index. The index must not become a sidebar; the current section uses `aria-current="location"`. Hash links support direct entry and reload. The page ends after the FAQ without duplicate board or contents buttons. The page loads its own feature translations lazily for en/ru/uk/pl. Registration follows three visible steps; open/closed team explanations and an application-page illustration, modifier details and scoring edge cases use labelled disclosures. Quiz and modifiers are separate sections with their own shortcuts: the quiz explains one-time answers, closure and personal rewards; modifiers explain effects, activation and restrictions. Registration timing, roster confirmation, restrictions on the active team and worked scoring examples remain visible in the main sections.

Guide sections compose the existing corner-framed `ItemCard`, `StatusBadge`, `DetailBlock`, `InlineNotice`, `Metric` and `OrnamentDivider` components. FAQ uses `AppAccordion` with explicit question/answer associations. Keep registration timing, readiness versus confirmation, the active-team modifier restriction, ordering/refund conditions and the separation of quiz currency from team results visible in the corresponding sections. Round guidance explains card opening, modifier ordering, preparation, gameplay, review and result presentation in sequence. Scoring visibly explains that negative round results accumulate until the end of the current game and reduce the best positive result, with an example showing that a later successful round does not erase earlier penalties. Rules must match current server behavior. Guide copy uses short, plain sentences without semicolons in all four locales. Guide layout and emphasis stay within this feature without changing the application reference or global control typography.

Illustrations sit in recessed, bordered `DetailBlock` figures with their captions, so screenshots remain distinct from live controls. They use deterministic demonstration data, not player records. They are localized product assets under `frontend/public/images/game-guide`; their preview uses `AppDialog` and horizontal scrolling on narrow screens. ## Board scope and existing responsive work

“Game board” means only the board cards and their arrangement, not the entire `/panel/game-board` page. The site header and the component above the board are separate components. ## Ownership and boundaries

### Typography and density

The common compact scale applies to every panel page, including application registration and its dialogs. Preserve the reference's materials, composition, interactions and state handling while using the same type and spacing roles as the rest of the application. Prefer reclaiming padding and redundant header height to shrinking readable content or controls below usable targets.

`uiTokens.type` is the source for text sizes in rem; MUI typography variants assign those sizes to roles. Use `Typography` variants instead of local font-size overrides. HTML heading levels express document structure independently of their visual variant.

| Role                                 | Size at the default root size | Variant                |
| ------------------------------------ | ----------------------------- | ---------------------- |
| Page and dialog title                | 24px                          | h3/h4                  |
| Main section or team title           | 20px                          | h5                     |
| Subsection, list heading, disclosure | 18px                          | h6/subtitle1           |
| Main reading text and item name      | 16px                          | body1/subtitle2        |
| Supporting text, actions, help       | 14px                          | body2/caption/button   |
| Short metadata and overlines         | 12px                          | overline/compact badge |
| Display emphasis                     | 32px                          | h1/h2                  |

Main text uses a 1.5 line height and headings 1.25. Display sizes are not a default for page panels. Brand marks, illustrations and card-matrix geometry may own their visual scale; ordinary form controls and section headings do not inherit that exception.

Titles embedded in briefing/list panels use the 18px panel-heading role, including the team queue title even when it is the page's semantic h1. Heading level alone does not justify making an embedded panel title larger than comparable quiz, history or modifier panels.

Panel inner padding is 12px; dense lists use 8px. Related controls use 8px gaps and sections normally 12px. Headers take the space needed by their text/actions without an empty minimum-height row. The modifier workspace pairs its compact search/filter toolbar with the active-list heading at the same height and keeps category starts aligned.

Search/filter toolbars use the existing compact field density: 36px controls and 14px text for a fine pointer, at least 44px controls and 16px field text for a coarse pointer. Small buttons follow the same 36/44px target rule. Standard editing fields, primary actions and icon controls retain 44px targets. Floating labels, focus, full translated text and keyboard operation remain available. A narrower viewport alone does not introduce a smaller font size.

Panel page insets belong to `MainLayout`: 12px below 600px and 16px from 600px on all edges. The mobile management controls reserve their additional bottom space. `PageShell` owns width, centering and composition without adding a second inset; the application reference retains its explicit inner inset. Viewport-sized panels read the actual main bottom inset instead of assuming 24px. Independently scrolling centered lists reserve stable thin scrollbar gutters on both edges, and paired tools/results use matching horizontal insets. Short standings tables retain their full row width without an empty scrollbar strip.

Draft modifier rows use stable selection/preview callbacks and memoization, matching draft questions. The shared modifier row places its optional selection control beside the name and keeps the details action on the right, avoiding a second action row. A native disabled fieldset blocks list interaction during a save without rerendering every row.

| Owner                              | Responsibility                                                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `shared/theme`                     | Palette, typography, control scale, materials, surface and side-panel tokens                                         |
| `shared/ui/primitives/<family>`    | Control appearance, internal slots, interaction and focus states; family theme overrides live beside implementations |
| `shared/ui/feedback`               | Dialog composition, confirmations, notices, progress and help                                                        |
| `shared/ui/patterns`               | Layout, navigation, lists, tables and reusable compositions                                                          |
| `shared/game-ui`                   | Reusable domain presentation: board matrix, participants, played cards, round score breakdown                        |
| Features                           | API/data, permissions, business state, translated labels, ordering and domain geometry                               |
| `app/theme/component-overrides.ts` | Assembles family overrides and the base document/material theme                                                      |

A page may use Box, Stack, Typography, icons, Collapse, ClickAwayListener and theme hooks as layout/implementation utilities. Interactive controls come from the common library. Do not add a feature-specific button, input, menu, dialog or badge implementation. First reuse a suitable existing component; introduce a common variant only for a demonstrated need that composition cannot satisfy, migrate consumers, and remove the superseded implementation. Generic shared UI must not import features, API, auth or game UI.

Page `sx` owns placement and external spacing. A component owns its internals. Do not reach into `.MuiDialog-*`, repaint supplied child buttons, copy surface recipes or append selector overrides to fix a variant. Shared theme files are the single source of corresponding MUI states. Board/card visuals may own domain geometry; this does not authorize a separate form theme.

`npm run check:ui-architecture` checks these boundaries, an explicit MUI foundation allowlist (including aliases/subpaths/re-exports and namespace/dynamic import restrictions), native controls outside the library, and control-slot/descendant-button repainting. These checks supplement source review; they do not prove visual or behavioral correctness. Its rule fixtures run before the repository scan.
